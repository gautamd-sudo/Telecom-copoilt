# Real-Time Event Pipeline (Kafka)

## 1. Overview
The Telecom AI Command Center relies on Apache Kafka as its high-throughput, low-latency event backbone. This decouples event ingestion, processing, alerting, and AI prediction.

## 2. Topic Architecture
The system employs domain-partitioned topics to maintain strict ordering per entity:
- `network.metrics`: High-frequency streaming data (throughput, latency, packet loss).
- `network.events`: State changes, topology updates, cell status.
- `network.alarms`: Fault management (active, cleared, acknowledged).
- `network.incidents`: Aggregated incident tracking and ticketing.
- `customer.events`: User equipment (UE) attach/detach, dropped calls, handover metrics.
- `ai.predictions`: Outputs from the ML layer (e.g., predicted cell failure in 4 hours).
- `ai.recommendations`: Prescriptive actions generated by the system.
- `notifications`: Egress queue for emails, SMS, and webhook dispatches.

## 3. Resilience & Guarantees
### 3.1 Idempotency & Duplicate Tolerance
- **Producers**: Configured with `idempotent: true` and `maxInFlightRequests: 1` to ensure strict ordering during network retries.
- **Consumers**: Database interactions are wrapped in idempotency checks (`eventId` or `[tenantId, source, sourceEventId]`). If a Kafka consumer crashes before committing an offset, re-processing the same message results in a no-op at the database level.

### 3.2 Error Handling & Dead Letter Queues (DLQ)
- **Transient Failures**: If a database outage occurs, consumers throw a `PrismaClientKnownRequestError`. `Kafkajs` natively catches this and initiates an exponential backoff retry.
- **Poison Pills (Schema Failures)**: If a payload fails `Zod` validation or causes a deterministic logic error, it is skipped and immediately routed to a DLQ topic (and written to the `DeadLetterQueue` DB table) with the `errorReason` attached. The offset is committed so the partition does not block.

### 3.3 Out-of-Order Events
State machines (like active Alarms) include internal timestamp validation. If an event arrives with a `timestamp` older than the currently persisted state, it is safely discarded.

## 4. Message Schemas & Telemetry
- **Zod Validation**: All payloads conform to heavily typed `Zod` schemas (e.g., `NetworkMetricEventSchema`).
- **Versioning**: Every event includes a `version` (e.g., `v1`).
- **Correlation & Auditing**: Events require an `eventId` (UUIDv4) and `tenantId`. Headers propagate these correlation IDs across microservices for distributed tracing.
